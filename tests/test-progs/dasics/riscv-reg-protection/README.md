# 寄存器保护微基准

在固定 `v5_full` O3 配置下测量软件保存、清零和恢复寄存器的成本。
程序使用 RV64 Linux SE 模式，通过普通调用边界研究寄存器保护，
不依赖 DASICS CSR 或访问检查。

## 实验入口与结论概览

后续实验先确认本文的前端配置约束，再按测量目标选择入口。
连续调用采用前端修正后的结果作为基线；首轮结果用于解释配置修正的影响。

| 实验入口 | 测量目标与口径 | 已验证结论 |
| --- | --- | --- |
| [`run.py`](run.py) | 热态连续调用，比较 SR、SCR 和不同 VLEN，减去匹配调用框架 | 清零及必要控制操作增加开销；不同集合的增量不能简单相加 |
| [`restore.py`](restore.py) | 排除 Store Queue 转发，单独测量从 L1、L2、DRAM 恢复 | 保存区位置显著影响恢复成本，宽向量的下层数据搬运成本更高 |
| [`pressure.py`](pressure.py) | 固定每次调用的加载数，改变被调函数工作集，比较 B 与 GF_SCR | 保存区与函数数据竞争 L1，保护增量在容量边界附近出现峰值，并不随工作集单调增加 |

三个入口分别回答热态保护序列、孤立恢复延迟和完整调用中缓存干扰的问题，
不能直接将它们的周期数相加或相互替代。当前结果支持同时研究保护指令、
保存区驻留和缓存竞争；硬件优化方案的收益仍待验证。

现有寄存器保护实验的 L1D 容量均为 64 KiB。改变数据驻留层级或工作集
不等于扫描缓存容量、相联度或 SQ/ROB 大小，尚无这些硬件参数的独立
性能归因结果。实际 CalculiX 保护调用的整程序开销也尚未测量。

## 实验定义

| 集合 | 寄存器 |
| --- | --- |
| G | `t0–t6`、`s0–s11`，19 个整数寄存器 |
| F | `ft0–ft11`、`fs0–fs11`，24 个浮点寄存器 |
| GF | G 和 F |
| V | `v0–v31`，32 个向量寄存器 |
| GFV | G、F 和 V |

`SR` 执行保存、调用和恢复；`SCR` 在调用前增加清零。
`B` 使用相同调用框架，不搬运目标寄存器。
`VCTL` 仅执行向量清零所需的 `vl/vtype` 临时配置和恢复，
用于观察控制指令的影响。

汇编使用微基准专用调用约定：`a0/a1` 承载参数和返回值，
`a2–a7` 保留给循环、上下文和被调用函数指针。
该调用框架用于匹配测量条件；接入实际库函数时需要另行适配完整 ABI。

标量组使用 VLEN=128。向量组、组合组及对应基线使用
VLEN=128、256、512、1024；ELEN 固定为 64。
每组运行空函数 `empty` 和固定计算函数 `compute`。

| VLEN，位 | 单个向量寄存器 | 32 个寄存器保存量 | 保存与恢复逻辑字节 |
| ---: | ---: | ---: | ---: |
| 128 | 16 B | 512 B | 1024 B |
| 256 | 32 B | 1024 B | 2048 B |
| 512 | 64 B | 2048 B | 4096 B |
| 1024 | 128 B | 4096 B | 8192 B |

G 和 F 的单向数据量分别为 152 B 和 192 B。
GF 的保存与恢复合计为 688 B。逻辑字节不等于缓存或 DRAM 流量。

## 向量状态

向量使用四组 `vs8r.v` 和 `vl8re8.v` 保存、恢复全部寄存器。
清零临时使用 `e8,m8,vl=VLMAX`，覆盖全部向量位，
随后在被调用函数入口前恢复原有 `vl/vtype`。

调用边界要求 `vstart=0`，不使用向量参数或向量返回值。
正常调用允许被调用函数改变 `vl/vtype/vcsr`，不执行额外的跨调用恢复。
本测试不模拟任意中断现场的完整上下文切换。

## 测量和校验

每个 VLEN 的独立正确性检查通过后，才启动计时作业。
检查覆盖完整位模式恢复、SCR 入口清零、调用返回值和保存区边界。

汇编循环通过 `m5_work_begin` 和 `m5_work_end` 标记统计区间。
配置脚本在开始事件执行 `m5.stats.reset()`，结束事件执行
`m5.stats.dump()`。初始化、预热和校验位于区间之外。
每批仅使用一对标记，默认预热 128 次，分别测量 1024 和 4096 次循环。

```text
增量周期/次 = (保护组 ROI 周期 - 匹配基线 ROI 周期) / 循环次数
```

基线按 VLEN、被调用函数和循环次数匹配。SCR 与 SR 的差值包含
清零及其必要控制操作；它们在乱序流水线中可能与其他工作重叠。
同时保留原始周期、提交指令和微操作数、存储转发、LSQ 和缓存统计。
汇总表的每逻辑字节周期仅按目标寄存器数据量归一化，不表示实际内存带宽。
1024 与 4096 次结果的差异用于检查固定开销是否已充分摊薄。

每个作业保留命令、开始和结束时间、退出码、guest 输出、`config.ini`、
完整 `stats.txt`、区间专用 `roi-stats.txt` 和 `roi.json`。
批次汇总保存在 `results.csv`、`results.json`、`summary.csv` 和
`summary.json`。

## 单次恢复的缓存层级实验

该入口单独测量一次寄存器恢复，不包含保存、清零、缓存准备和结果检查。
它使用独立 ELF，并保留前述连续调用微基准。

先编译并运行小规模预检，确认标记顺序、寄存器结果和缓存来源：

```bash
make -C src restore -j2
python3 restore.py --jobs 12 --vlen 128 --samples 2 \
    --output-dir build/runs/restore-check-001
```

预检通过后运行完整矩阵：

```bash
python3 restore.py --jobs 40 --samples 32 \
    --output-dir build/runs/restore-001
```

复现时先查看`finalrun.json`的`status`和`returncode`，再查看
`summary.csv`的周期分布及`results.csv`的逐样本来源证据。
成功要求所有作业和样本均为PASS；框架不会将来源不符的样本计为有效结果。
`build/`中的原始数据不纳入Git，本文保留测量条件和结果摘要。

默认测试整数19个、浮点24个，以及VLEN=128/256/512/1024的32个向量寄存器。
整数与浮点使用VLEN=128；每种VLEN和数据来源都有匹配的空段B。
共30个作业，每个作业32个独立样本。

| `--source` | 每次恢复前的数据状态 |
| --- | --- |
| `l1` | 保存区驻留L1D，Store Queue排空 |
| `l2` | 保存区从L1D失效、驻留L2，Store Queue排空 |
| `dram` | 保存区从各级数据缓存失效，Store Queue排空 |

三种条件使用相同的v5_full配置和64 KiB L1D。数据路径的L1D、L2、L3
预取均关闭，指令缓存和地址翻译保留。DRAM条件指请求实际到达DRAM，
不指定DRAM行缓冲的初始开闭状态。

每个样本先预读源数据、将目标寄存器置为不同值，随后进入PREP标记。
Python端排空流水线，按L1D→L2→L3顺序写回，并失效所选层级。
PREP后的串行化CSR读阻止排空过程提前执行被测加载；独立START才重置
统计，END立即保存该样本的统计。CSR读只作边界保护，不用于计时。
每个样本都重新准备，避免只有第一轮冷、后续全热。

START至END之间的内存操作仅为目标寄存器加载。向量包含必要的地址递增，
所有组包含匹配的控制分支和标记。B用于估计这个测量框架的开销。
gem5伪指令会改写a0，因此每个标记前均显式设置work ID和thread ID。

数据来源按实际统计验收：目标缓存线的首次缺失、下层命中或DRAM读取
必须符合所选条件，并要求没有Store Queue转发、指令缓存缺失和可观测
的地址翻译缺失。整数、浮点源区沿用原有偏移，分别跨3和4条64 B缓存线；
向量跨8/16/32/64条线。同一行内的后续命中和MSHR请求合并属于正常行为。

输出包含每个样本的原始周期，以及减去同来源、同VLEN、同样本序号B的
净周期，按整组报告最小值、中位数、最大值。它描述孤立恢复延迟，
与连续调用微基准的平均增量口径不同。

### 缓存层级测量结果

2026-11-05，在`cmy-zgclab-eda`完成30个并行作业、960个样本。
其中576个样本执行目标寄存器恢复，其余为匹配的空段B。
所有功能、计时和数据来源检查通过；所有样本的Store Queue转发、
指令缓存缺失及可观测的ITB/DTB缺失均为0。

下表为整组寄存器的净恢复周期中位数，已扣除每个样本均为13周期的B。
DRAM括号内为32个样本的最小值和最大值；L1、L2组的样本值均相同。
CPU频率为2 GHz，每周期0.5 ns。

| 寄存器集合 | 有效数据量 | L1命中 | L1缺失、L2命中 | 各级缓存缺失、DRAM返回 |
| --- | ---: | ---: | ---: | ---: |
| 整数19个 | 152 B | 19 | 27 | 121（121–183） |
| 浮点24个 | 192 B | 23 | 31 | 131（131–193） |
| 向量32个，VLEN=128 | 512 B | 28 | 39 | 200（171–233） |
| 向量32个，VLEN=256 | 1024 B | 28 | 56 | 312（279–312） |
| 向量32个，VLEN=512 | 2048 B | 28 | 102 | 533（499–1233） |
| 向量32个，VLEN=1024 | 4096 B | 33 | 200 | 937（917–1569） |

来源证据按每个样本核对：L2组的新L1行请求数和L2命中数均为
3/4/8/16/32/64；DRAM组对应的L2缺失、L3缺失及DRAM读突发数也均为
这些数量，且内存控制器写队列转发为0。共同排空阶段每次只提交1条
边界指令，恢复加载未在准备阶段提前执行。三种来源下，同一寄存器
集合的提交指令数和微操作数一致。

DRAM长尾伴随刷新和排队变化。例如VLEN=512的一个样本比常见值多700周期，
同时刷新能量非零、平均排队明显增加；当前`tRFC=350000 ticks`恰为
700个CPU周期。范围统计保留这些有效样本，不将DRAM恢复描述为固定延迟。

整数、浮点和向量的整组大小不同，G/F还分别覆盖3/4条缓存线，
不能仅用总周期判断某种寄存器类型本身更慢。L1下VLEN=128/256/512
周期相同，仍受gem5按寄存器拆分微操作及未建模寄存器堆字节带宽的限制。
本配置各级缓存的tag/data/response延迟均为2/2/2周期，属于模拟假设。
SE地址转换不包含完整系统模式的页表遍历成本；DTB计数为0不代表验证了
真实硬件TLB的热态行为。

本次实验得到以下结论：

- 在统一排除Store Queue转发后，失去L1驻留仍显著增加恢复成本。
  整数19个寄存器的净周期从19增加到L2的27、DRAM的121；
  4 KiB向量状态从33增加到200、937，DRAM中位数约为L1的28.4倍。
- 宽向量的下层缓存和内存开销随缓存行数量增加，说明保存区的数据位置
  是评估软件保护成本的重要条件。L1下的平坦结果不代表真实寄存器堆
  加宽没有成本，仍需遵守当前向量时序模型的适用范围。
- 单次冷恢复和连续调用的增量采用不同口径。后续实验应同时记录
  缓存来源、转发行为和测量边界，分别评估热态和冷态保护路径。

样本明细见 [results.csv](build/runs/20261105-restore-full01/measurements/results.csv)，
原始及净周期范围见 [summary.csv](build/runs/20261105-restore-full01/measurements/summary.csv)，
运行日志见 [batch.log](build/runs/20261105-restore-full01/batch.log)。

## 被调函数的缓存压力实验

该实验测量细粒度保护调用中，软件保存区与被调函数数据竞争缓存后的
整次调用增量。使用原有 `B` 和 `GF_SCR` 调用框架；保护集合固定为
19 个整数寄存器和 24 个浮点寄存器，执行保存、清零和恢复。
本轮不包含向量寄存器，也不启用 DASICS 权限检查。

从本目录执行：

```bash
make -C src pressure -j3
python3 pressure.py --jobs 40 --max-ticks 100000000000 \
    --output-dir build/runs/pressure-001/measurements
python3 plot_pressure.py build/runs/pressure-001/measurements/summary.csv \
    --output-dir build/runs/pressure-001/figures
```

`pressure.py` 先执行独立功能检查，再运行性能矩阵。成功要求
`finalrun.json` 的 `status=PASS`、`returncode=0`，且
`convergence_status=PASS`。逐作业结果、配对结果、收敛比较分别保存在
`results.csv`、`summary.csv`、`n-comparison.csv`。绘图需要 Matplotlib。

### 负载与测量边界

| 项目 | 设置 |
| --- | --- |
| CPU / 缓存 | 修正后的 `v5_full`，2 GHz，L1D 64 KiB、L2 1 MiB、L3 2 MiB |
| 预取 | 沿用平台配置，不执行额外失效或排空 |
| 被调函数 | 固定随机指针链，每条 64 B 缓存线存放一个 next 指针 |
| 活跃工作集 W | 1、32、64、128、256 KiB |
| 每次调用工作量 | 4096 次串行依赖加载，返回地址校验和及最终链头 |
| 配对条件 | 同一 W、种子、调用次数、数据地址和校验值 |
| 随机排列 | 种子 0、1、2，逐个保留，不作为独立硬件重复试验 |
| 预热 / 测量 | 同一汇编循环先预热 8 次，再测量 N=32、64 次 |
| 统计区间 | 整批调用共用一对 `m5_work_begin/end`，由配置脚本 reset/dump |

所有组始终分配 256 KiB 指针缓冲区和同样大小的上下文，只改变前缀中
参与链表的缓存线数量。工作集变大不会增加被调函数的指令数或加载数，
也不会移动配对组的保存区和数据地址。预热与计时沿用同一调用位置，
期间不重新设置目标寄存器，不执行每次调用的标记、缓存失效或流水线排空。

初始化、指针环检查、入口清零检查、寄存器位模式与返回值校验均在 ROI
之外。功能入口额外记录被调函数入口状态；计时入口不执行这些记录。
每个计时作业结束后仍检查恢复状态、校验和及缓冲区边界。

主结果采用 N=64。N=32 用于检查每次调用的基线周期、保护周期、增量及
相对开销是否收敛，判据为两者差值相对 N=64 结果不超过 1%。

```text
增量周期/次 = (GF_SCR 的 ROI 周期 - B 的 ROI 周期) / N
相对开销 = (GF_SCR 的 ROI 周期 - B 的 ROI 周期) / B 的 ROI 周期
```

脚本还按实际提交统计检查工作量。令 K=4096，则 B 每批提交
`N × (4K + 31) + 8` 条指令，GF_SCR 为 `N × (4K + 160) + 8`。
两者每次调用相差 129 条指令，分别对应 43 次保存、43 次清零和
43 次恢复；额外加载和存储各为 43 次。

2026-11-05，在 `cmy-zgclab-eda` 完成 1 个独立功能作业和 60 个性能作业，
全部通过。功能作业覆盖全部工作集、种子和调用框架组合。全部配对的
地址、工作量及校验值检查通过。N=32 与 N=64 的四项指标最大相对变化
为 0.214%，通过 1% 收敛判据。

下表为 N=64 时三个固定种子的中位数，括号为最小值至最大值；
范围表示三种排列的差异，不是置信区间。周期均按整次调用计算。

| W | B 周期/次 | GF_SCR 周期/次 | 增量周期/次 | 相对开销 |
| ---: | ---: | ---: | ---: | ---: |
| 1 KiB | 12301.31 | 12352.27 | 50.95 | 0.414% |
| 32 KiB | 12301.31 | 12352.27 | 50.95 | 0.414% |
| 64 KiB | 12367.91 | 12614.83 | 246.88（245.94–246.92） | 1.996%（1.989–1.996%） |
| 128 KiB | 45070.45 | 45121.84 | 51.39（51.39–51.42） | 0.114% |

![三个固定种子的调用周期、保护增量和相对开销；64 KiB 出现峰值，128/256 KiB 的基线执行时间明显增加。](build/runs/20261105-pressure-full01/figures/pressure.png)

该结果中的保护增量随工作集变化并不单调。64 KiB 附近的增量最大；
128/256 KiB 时被调函数本身明显变慢，但保护组与基线的差值回到约
51 周期。相对开销下降不能解释为保护操作变得免费，需要同时查看
基线时间和增量时间。

按 ROI 统计归一化，每次调用的 L1D 新请求数如下。此处使用
`dcache.demandMshrMisses::total`，不包含合并到在途请求的 MSHR hit。

| W | B 新请求/次 | GF_SCR 新请求/次 | 两组差值 |
| ---: | ---: | ---: | ---: |
| 1、32 KiB | 0 | 0 | 0 |
| 64 KiB | 10.078 | 40.062–40.078 | 约 30 |
| 128、256 KiB | 4098.016 | 4104.016 | 6 |

这些请求在 L2 全部命中，L3 demand 访问和 DRAM 读取均为 0。
L1D 预取器在本负载下没有发出请求。64 KiB 的额外行请求明显多于
128/256 KiB，支持容量边界附近缓存干扰被放大的解释。大工作集下，
基线本身已经承受大量缺失，保护访问增加的行请求反而较少。
全 ROI 的缓存计数混合了指针链、寄存器保存区和调用框架元数据，
精确归属需要下面的逐行诊断。

### 保存区逐行诊断

另取种子 0、N=32 的 GF_SCR，在 W=1、64、256 KiB 下重放原始命令，
只增加有界的 `Exec,ExecFetchSeq,LSQUnit,Cache` 日志。三组重放的 ROI
起止 tick、周期数和程序结果与正式测量一致，未改变硬件参数或 guest。
轨迹覆盖 ROI 开始前 1000000 ticks 至开始后约 2.5 次调用；只分析其中
前两次完整计时调用。

通过保存指令 PC、LSQ 序号和写回物理地址，将目标寄存器保存区映射为
6 条物理缓存线：`0x80080380`、`0x800803c0`、`0x80080400`、
`0x80080440`、`0x80080480`、`0x800804c0`，对应 L1D 的 set 14–19。
调用框架元数据另行分类，不计入这 6 条线。每个完整调用均包含 43 次
目标保存、43 次目标恢复和 4096 次已提交的指针链加载。

| W | 目标恢复加载 | 保存区逐出 / 重填行数 | 指针链的新行请求，调用 1 / 2 |
| ---: | --- | ---: | ---: |
| 1 KiB | 43 次 L1D 命中 | 0 / 0 | 0 / 0 |
| 64 KiB | 6 条线从 L2 取回，其余请求命中或合并 | 6 / 6 | 36 / 32 |
| 256 KiB | 6 条线从 L2 取回，其余请求命中或合并 | 6 / 6 | 4096 / 4096 |

六个调用中，目标恢复均未使用 Store Queue 转发。较大两个工作集下，
可逐行观察到保存区在被调函数执行期间从 L1D 逐出，随后恢复读取
触发 L1D 缺失、L2 命中和重填。全 ROI 中的少量转发属于框架元数据，
不能据此判断寄存器载荷也发生了转发。

64 KiB 的第二次调用中，保存区对应的 6 个 set 各有 4 次指针链新请求，
框架元数据对应的另外 2 个 set 也各有 4 次。这个分布直接显示了
保存区与函数数据的 set 竞争。第一次调用保留了 ROI 边界附近的额外
请求，因此不将短轨迹的第一轮数值当成稳态均值。

64 KiB 与 256 KiB 都需要取回 6 条保存区缓存线，却有明显不同的整体
增量。原因分析必须包含被调函数的缓存行为：前者的保存区会干扰原本
能够驻留的指针链；后者的 4096 次链式读取本就全部缺失。
逐行证据与配对统计共同支持这一解释，但没有把每一个额外周期分别
分配给恢复、缓存竞争或乱序重叠。

原始命令和窗口见 [trace-plan.json](build/runs/20261105-pressure-full01/diagnostics/trace-plan.json)，
逐行事件及调用归属见 [analysis.json](build/runs/20261105-pressure-full01/diagnostics/analysis.json)，
诊断日志见 [batch.log](build/runs/20261105-pressure-full01/diagnostics/batch.log)。

该负载用于观察固定工作量下的缓存竞争，不代表 CalculiX 的函数分布、
实际保护调用频率或全部 DASICS 开销。整次调用差值包含保护指令与
被调函数之间的相互影响，不能直接等同于孤立的寄存器恢复延迟，也不能
将所有额外缓存缺失都归为恢复读取。

## 模型适用范围

现有 gem5 whole-register 指令按向量寄存器拆分微操作。
保存和恢复全部 32 个寄存器共 8 条架构指令、64 个访存微操作，
请求字节数随 VLEN 增加。VLEN=1024 时，一个寄存器的 128 B 请求
可能拆分为两个 64 B 缓存行请求；完整存储转发可绕过该缓存访问路径。

当前寄存器堆没有按字节计费的端口带宽模型，向量功能单元延迟也不随
VLEN 自动增加。因此结果用于研究软件序列、数据量、访存和窗口压力，
不能直接推导真实向量寄存器堆端口、面积或频率。
VLEN 大于 128 的配置属于扩展实验配置。

### 前端配置约束

公共配置启用 `decoupledFrontEnd`，并设置 `requiresBTBHit=True`。
[`BAC::createFetchTarget`](../../../../src/cpu/o3/bac.cc) 依赖 BTB 条目
提前识别分支。若使用首轮的 `requiresBTBHit=False`，
[`BPredUnit::updateBTB`](../../../../src/cpu/pred/bpred_unit.cc) 会跳过
返回指令，以及配置了间接预测器时的间接跳转，导致这些指令无法正常
进入提前预测流程。设置为 True 后允许建立对应条目，RAS 和 ITTAGE
仍分别提供返回地址和间接目标。

首轮 VLEN=128、`B/empty`、4096 次循环的 ROI 中，
`mispredictDueToBTBMiss_0::CallIndirect` 和 `::Return` 各为 8192。
对应的 BTB 类型查询计数均为 0。修正后，这两项 BTB 缺失计数均为 0，
总恢复次数从 16387 降至 3。首轮结果保留用于配置修正前后的对照。

`commit.branchMispredicts` 还可能包含向量配置造成的完整 PCState
不匹配，不能全部解释为跳转地址预测错误。
