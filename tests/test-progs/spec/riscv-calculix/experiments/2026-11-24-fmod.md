# CalculiX 的 fmod 寄存器保护实验

2026-11-23 至 2026-11-24。在 `v5_full` O3 上运行 SPEC CPU2006 `454.calculix -i beampic`，对齐布局后，G+F 硬件门将一次真实 `fmod` 往返从平均 **401.04 周期**缩短到 **343.72 周期**，降幅 **14.29%**。585 对调用全部缩短，其中 580 对恰好节省 57 周期。整程序节省 **43,830 周期（0.0385%）**。[585 对调用的原始 tick 和周期](2026-11-24-fmod-paired-calls.csv)

## 平台和保护边界

gem5 26.0.0.0，RV64 Linux SE，单硬件线程，`v5_full` O3、2 GHz、500 ticks/周期。静态应用使用 RV64GC/LP64D，ELF 记录的 GCC 版本为 13.3.0。调用来自 SPOOLES 的 `Drand_setSeed` 和 `Drand_value`。两版使用同一套 CalculiX 应用对象和同一工具链中的 `fmod` 实现。[平台配置](../../../../../configs/spec/riscv_se_dasics_v5_full.py) · [构建规则](../protected/Makefile)

两种门都通过 `fa0/fa1` 传入被除数和除数，由 `fa0` 返回浮点余数。B 使用私有栈、私有浮点环境，能够读取辅助函数的 256 字节查找表和单个 8 字节 GOT 表项。软件门保存、清零、恢复 `s0–s11` 和 `fs0–fs11`，共 72 条指令。G+F 门用两条全掩码 `PROREG` 和一条 `LEAVE` 完成同一策略。两者均通过 `DASICSCALL` 进入 B。本实验覆盖 `beampic` 实际经过的数值路径，数学错误路径配置为终止仿真。[调用门](../protected/gate.S) · [保护区链接布局](../protected/link.ld)

## 布局如何改变整程序结果

下表的**节省周期 = 软件门周期 − G+F 门周期**。百分比以同一行的软件门为分母。

| ELF 布局 | 软件门整程序周期 | G+F 门整程序周期 | 节省周期 | 节省比例 |
| --- | ---: | ---: | ---: | ---: |
| 各按门的实际尺寸链接 | 113,370,224 | 113,749,272 | −379,048 | −0.3343% |
| 两种门均预留 640 字节 | 113,977,567 | 113,933,737 | +43,830 | +0.0385% |

软件门的代码长 588 字节，G+F 门长 312 字节。初版的长度差还改变了链接器对其他调用指令的编码选择，使门之前的调用点也移动了。对齐版在最终 `ret` **之后**分别填充 52 和 328 字节，执行路径沿用各自的指令序列。下表列出几个实际链接地址。

| 位置 | 对齐前软件门 | 对齐前 G+F 门 | 对齐后两版 |
| --- | ---: | ---: | ---: |
| `Drand_value` 入口 | `0x1087e0` | `0x1087d4` | `0x1087e4` |
| 可信调用门入口 | `0x108adc` | `0x108ad0` | `0x108ae0` |
| 真实 `fmod` 入口 | `0x1a2978` | `0x1a2858` | `0x1a29b0` |
| 私有查找表 | `0x1a2cc0` | `0x1a2ba0` | `0x1a2cf8` |
| B 栈顶 | `0x273000` | `0x272000` | `0x273000` |

对齐检查逐一比对了 9 个静态调用点及其返回地址。除门所在的 640 字节和 GNU build ID 内容外，两份 ELF 的已分配节具有相同的布局和内容。门内部的指令地址仍随实现而异。两批实验中，G+F 门的整程序提交指令数均比软件门少 **40,365 = 585 × 69** 条，但两批整程序周期差的符号相反，所以用对齐版作逐调用计时基线。[布局检查](../protected/check_layout.py)

## 585 次调用的配对结果

计时窗口从调用方的 `jal` **提交**开始，到返回后调用方位于 `PC+4` 的第一条指令**提交**结束。用 gem5 的 `RetiredInstsPC` 记录模拟 tick，按调用点和该点的执行序号配对，并核对两版的全局调用顺序。每次往返周期等于两端 tick 之差除以 500。9 个静态调用点中，本次输入执行了以下 3 个。[配对与校验脚本](../protected/paired_calls.py)

| 调用点 | 调用指令 PC | 次数 | 软件门平均周期 | G+F 平均周期 | 平均节省 | 节省中位数 | 合计节省 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `Drand_setSeed` 初始化种子 | `0x1086da` | 3 | 673.67 | 553.33 | 120.33 | 58 | 361 |
| `Drand_value` 更新第一个种子 | `0x10892a` | 291 | 400.84 | 343.87 | 56.97 | 57 | 16,579 |
| `Drand_value` 更新第二个种子 | `0x108944` | 291 | 398.43 | 341.42 | 57.01 | 57 | 16,589 |
| **全部** | | **585** | **401.04** | **343.72** | **57.31** | **57** | **33,529** |

每次节省量的完整分布为 49 周期 1 次、57 周期 580 次、58 周期 2 次、59 周期 1 次、245 周期 1 次。首次种子初始化从 1,202 周期降到 957 周期，这一对拉高了初始化组的均值。

585 个窗口累计耗时从 234,608 周期降至 201,079 周期，窗口内收益为 **33,529 周期**。这些窗口只占软件门整程序周期的 0.206%。14.29% 是调用往返的耗时降幅，0.0385% 是整程序降幅。

## 窗口之外的 10,301 周期

首次调用前，两版都运行了 72,078,353 周期。584 个相邻调用间隙合计节省 **69 周期**。最后一次调用返回到程序退出，耗时从 40,820,851 降至 40,810,619 周期，节省 **10,232 周期**，占窗口外差值的 99.33%。四段之和为 **0 + 33,529 + 69 + 10,232 = 43,830**。以下逐层分析最后一段。

### 尾段快照与 O3 停调

在对齐 ELF 的 `0x108948` 第 291 次提交时保存累计统计，继续运行到正常退出，以终点减去快照。快照取在该 CPU tick 完成后，包含同一 tick 内的其他提交。软件门的截点为 36,578,357,000 tick，G+F 为 36,561,558,000 tick，均与逐调用记录中的最后一次返回相符。尾段两版各提交 **60,124,848 条指令**，加载和存储也各自相同。[截点与累计计数校验](../protected/tail_stats.py)

| 尾段周期分类 | 软件门 | G+F | 节省周期 |
| --- | ---: | ---: | ---: |
| O3 暂停调度 CPU tick | 89,134 | 83,213 | **+5,921** |
| Commit 采样，当周期提交 0 条 | 19,079,466 | 19,075,600 | +3,866 |
| Commit 采样，当周期至少提交 1 条 | 21,308,302 | 21,307,791 | +511 |
| CPU 已调度，当周期无 Commit 采样 | 343,949 | 344,015 | −66 |
| **合计** | **40,820,851** | **40,810,619** | **+10,232** |

对每个停调区间，分别记录暂停 tick、首次实际重新调度 CPU 的回调及其 tick、下一 CPU 时钟沿。按 `idleCycles` 的规则计入两个时钟沿之间跳过的周期，零记账区间也保留。两版全部 1,914 段都有对应的唤醒事件。下表按**结束等待的回调**归类，同一段期间也可能有其他请求在途。[区间配对与记账](../protected/idle_spans.py)

| 有效唤醒来源 | 软件门段数 | G+F 段数 | 软件门等待周期 | G+F 等待周期 | 节省周期 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 取指响应 | 886 | 836 | 82,934 | 76,104 | **+6,830** |
| 数据加载响应 | 59 | 58 | 3,611 | 3,475 | +136 |
| 数据存储响应 | 34 | 37 | 2,577 | 3,622 | −1,045 |
| 执行单元完成 | 2 | 2 | 12 | 12 | 0 |
| **合计** | **981** | **933** | **89,134** | **83,213** | **+5,921** |

取指等待净少 **50 段**，每段平均从 93.60 降至 91.03 周期。数据响应结束的等待则净增加 909 周期。两者相抵得到表中的 5,921 周期。

### 取指回包能解释多少停调差异

以 I-cache **成功接受请求**为起点，比较同一 32 字节取指块的响应延迟。为区分循环中对同一块的多次访问，用该回包供给的第一条来源明确且最终提交的指令，将其 PC、相对截点的退休序号和取指块地址一起配对。两版都停调的 596 对对段数差贡献为零。下表展开其余事件，其中“阈值”指相对请求发出、对照版实际开始暂停的时刻。[请求提取](../protected/fetch_requests.py) · [动态配对](../protected/fetch_pairs.py)

| 同块请求的观察结果 | 软件侧停调数 | G+F 侧停调数 | 净少段数 |
| --- | ---: | ---: | ---: |
| 未停调版在对照暂停阈值之前已收到回包 | 168 | 136 | **+32** |
| 未停调版保持调度超过对照阈值 | 5 | 7 | −2 |
| 回包与对照阈值同刻 | 1 | 1 | 0 |
| 请求期间还有其他停调或已有停调 | 27 | 23 | +4 |
| 缺少可唯一配对的退休指令 | 89 | 73 | +16 |
| **合计** | **290** | **240** | **+50** |

第一行的 **304 对**解释 32 段净差和 **5,637 个净等待周期**，属于上述 6,830 个取指等待收益周期。另有 554 对两版均停调且区间内无其他停调干扰，合计节省 1,891 周期，其中 1,708 周期来自回包延迟缩短，183 周期来自发出请求后更晚才暂停。其余请求包含收益和反方向变化，需保留各自的符号。

### 缓存层级、预取提前量和排队

对这 304 对请求逐级回放，按各版成功发送 tick、发起 PC 和取指块找到 L1I 事务，再按实际 64 字节物理缓存行和请求标识追到 L2、L3 和内存控制器。需求合并到已有 MSHR 时，沿最先发起填充的请求继续向下追踪。608 条路径均能还原；发生停调的一侧全部等到了 DRAM 填充。[缓存轨迹提取](../protected/cache_ingest.py) · [路径分析](../protected/cache_paths.py)

| 提前回包一侧的数据来源 | G+F 提前，软件门停调 | 软件门提前，G+F 停调 | G+F 净少停调 |
| --- | ---: | ---: | ---: |
| L1I 命中 | 79 | 57 | **+22** |
| L2 命中 | 52 | 41 | +11 |
| L3 命中 | 2 | 12 | −10 |
| 两侧的填充都来自 DRAM | 35 | 26 | +9 |
| **合计** | **168** | **136** | **+32** |

以取指块 `0xe60e0` 为例，软件门在三级缓存逐级新建缺失，请求发出后第 44 周期暂停，第 136 周期收到回包。G+F 访问同一物理行时直接命中 L1I，2 周期返回。就这 168 对正向样本而言，G+F 的 79 次 L1I 命中有 63 次能确认缓存行由预取填入，52 次 L2 命中有 50 次在命中时仍带有首次使用的预取标记。

预取也能缩短两侧都从 DRAM 取数的等待。在正向样本中，有 26 对在两版的 L1I 都合并到了在途预取，且两侧都依赖 DRAM 填充。需求到达时，G+F 的预取平均已向下游发出 **106.85 周期**，软件门为 **32.69 周期**。需求随后等待填充的时间分别为 **18.27** 和 **144.62 周期**。

在全部 168 对正向样本中，从需求到达后开始计算，DRAM 读请求入队到调度器选中的等待平均为软件门 **31.98 周期**、G+F **0 周期**。在 136 对反向样本中，G+F 为 12.01 周期、软件门为 0 周期。各组缓存 MSHR 就绪后等待下游接受的平均时间均低于 0.1 周期。DRAM 排队时间已计入填充等待；均值的分母含该方向的全部请求，包括片上命中。[路径时间分解](../protected/cache_report.py)

### 归因边界

本次输入的窗口外收益几乎都出现在最后一次返回之后。其中可直接归到停调记账的收益以取指回包更及时为主。缓存证据把可配对的 32 段净差追到了数据驻留层级或相对需求的预取进度。仍待定位的是门内哪次执行时序变化最先改变了后续取指与预取轨迹，以及尾段另外 **4,311 个已调度周期**的具体硬件成因。其余 **18 段取指净差**涉及阈值、重叠停调和缺少唯一配对等情形，304 对缓存结果只适用于所选的提前回包样本。

## 校验和复现

初版布局、对齐基线和逐调用计时三批各运行两种门，六次运行均自然退出，退出码为 0。`beampic.dat` 和 `SPECtestformatmodifier_z.txt` 均按用例原有的 `specdiff` 容差通过。每版的跨域调用、真实 `fmod` 入口、可信返回门入口及末尾均提交 585 次。G+F 版的两条 `PROREG` 和一条 `LEAVE` 分别提交 585 次，两版数学错误入口的计数均为 0。[SPEC 比较规则](../workload.json)

开启逐次跟踪后，两版各自的整程序周期和提交指令数都与对齐基线完全相同。软件门为 113,977,567 周期、178,860,362 条指令，G+F 门为 113,933,737 周期、178,819,997 条指令。

按 SPEC 公共说明准备本地源码、输入、参考输出和比较工具，然后从仓库根目录复现对齐版。若普通版对象与 SPEC 资产位于另一个工作区，构建普通版时使用该用例目录，两条受保护测试命令均传入 `ORDINARY_CASE`。[资产准备](../../README.md#本地资产) · [用例说明](../README.md)

```bash
case_dir="$PWD/tests/test-progs/spec/riscv-calculix"
elf_dir="$case_dir/build/protected-fmod"
batch="$case_dir/build/runs/fmod-$(date +%Y%m%d-%H%M%S)"
make riscv-dasics
make -j46 -C "$case_dir"
make -j2 -C "$case_dir/protected" check OUT="$elf_dir" RUN_DIR="$batch/reference"
make -j2 -C "$case_dir/protected" time-calls OUT="$elf_dir" \
    BASELINE="$batch/reference" RUN_DIR="$batch/timed"
```

原始批次位于用例的本地 `build/runs/` 目录。初版布局见 `20261123-fmod-gate-01`，对齐基线见 `20261123-fmod-layout-01`，逐调用测量见 `20261124-fmod-paired-01`。各批次的 `functional/{sw,gf}/m5out/stats.txt` 记录整程序统计，计时批次的 `m5out/retire.log` 记录退休事件。归档 CSV 的每一行均包含两版的起止 tick，可独立重算往返周期和配对差值。[归档 CSV](2026-11-24-fmod-paired-calls.csv)

### 复现窗口外的四轮回放

以下命令接续上面的 `time-calls`，保持同一对 ELF 的绝对路径。默认 SPEC 资产位于当前用例所属的 `spec/` 目录。使用外部资产时，将 `assets` 设为含普通版 `riscv-calculix/` 和 `tools/specdiff-runtime/` 的 SPEC 根目录。每轮为两版创建新的输出目录，再读取相应基线分析。

```bash
assets="$(dirname "$case_dir")"
run_replay() (
    set -eu
    stage="$1"
    analyzer="$2"
    baseline="$3"
    shift 3
    out="$batch/$stage"
    run_gate() {
        python3 -B "$case_dir/protected/check.py" "$1" \
            --elf "$elf_dir/calculix-$1.elf" --assets "$assets" \
            --outdir "$out/functional/$1" "${@:2}"
    }
    run_gate sw "$@" & sw=$!
    run_gate gf "$@" & gf=$!
    rc=0
    wait "$sw" || rc=$?
    wait "$gf" || rc=$?
    [ "$rc" -eq 0 ] || exit "$rc"
    python3 -B "$case_dir/protected/$analyzer.py" \
        --runs "$out/functional" --baseline "$baseline" --outdir "$out"
)
run_replay tail tail_stats "$batch/timed/functional" --tail-stats &&
run_replay wake idle_spans "$batch/tail/functional" --idle-wakes &&
run_replay fetch fetch_pairs "$batch/wake" --fetch-requests &&
run_replay cache cache_paths "$batch/fetch" --cache-pairs "$batch/fetch"
```

| 原始批次（用例的 `build/runs/` 下） | 输出与核对项 |
| --- | --- |
| `20261124-fmod-tail-01` | `tail-stats.csv`、`tail-summary.json`。两份累计快照的差值与退休日志的起止 tick 一致。 |
| `20261124-fmod-wake-01` | `wake-intervals.csv`、`wake-by-reason.csv`。逐段求和复现两版的 `timesIdled` 和 `idleCycles`。 |
| `20261124-fmod-fetch-01` | `fetch-pairs.csv`、`fetch-blocks.csv`、`fetch-summary.json`。两版比较覆盖全部 886 和 836 段取指停调，未配对事件单列。 |
| `20261124-fmod-cache-01` | `cache-pairs.csv`、`cache-levels.csv`、`cache-summary.json`。304 对请求覆盖 302 条物理缓存行，每条请求的发出、回包和退休位置均与取指批次吻合。 |

这四轮共八次运行均正常退出并通过两份 `specdiff` 比较。唤醒、取指与缓存回放分别核对截点和终点的 90 项累计计数，两版各自均与对应基线相同。截点和 168/136 的筛选条件绑定本次对齐 ELF 及 `beampic` 输入。布局或输入变化时需重新确认返回 PC、动态执行次数和可配对样本。
